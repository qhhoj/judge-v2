# Decisions

One line per decision: what, and why.

- The judge dials the bridge over gRPC with TLS: one typed contract for both sides, HTTP/2 backpressure, and the bridge stays reachable only from judge hosts.
- Changes inside protocol v1 are additive only: judges and bridges of different builds must keep talking.
- Results are numbered per assignment and acked cumulatively: a reconnect replays the outbox without double-applying a write.
- A resumed assignment does not spend the requeue: a short network drop must not count as a lost judge.
- `RETRY UNSPECIFIED` is capped at three per submission: a problem no judge can serve must end as an internal error, not loop. Transient reasons (DATA_UNAVAILABLE, RUNTIME_MISSING, SANDBOX_FAILURE) wait with a backoff outside the cap and end IE after the 30-minute deferral window, and UNSUPPORTED is a refusal: a data save or a judge hiccup is not a failure, and must not turn queued submissions into IE.
- Every problem-author program (checker, interactor, generator, signature entry) runs in isolate: problem data is not trusted.
- Output over the cap is OLE ahead of TLE: the JVM ignores SIGXFSZ and would otherwise run a print loop to the time limit.
- An unknown init.yml key is refused as UNSUPPORTED; an unknown checker arg is ignored, because refusing needs a production query for stray args first.
- Python 2 and 32-bit assembly are not supported: Python 2 is end of life and isolate's seccomp kills 32-bit binaries.
- Scratch is not supported: it needs its own runtime, and its problems are refused with `RETRY RUNTIME_MISSING`.
- The vendored testlib is C++ only: Pascal and Java checkers that include testlib do not compile.
- A contestant's unreadable OUTPUT zip is WA on every case: it is the contestant's mistake, not a judge fault.
- Releases publish only from a signed tag on main (2026-10-24, bug hunt infra): `packaging/check-release-tag.sh` gates the GitHub Release and the `:vX.Y.Z` image on an annotated `vX.Y.Z` tag whose signature GitHub verified, pointing at the built commit, which is on main. The tarball and every pushed image carry a build provenance attestation (`actions/attest-build-provenance`); installs verify it (`gh attestation verify`, DEPLOY.md step 8). Why: any `v*` tag published an unsigned release that hosts checked only against a checksum from the same release (P2-4).
- The image build pins protoc and `rustup-init` by sha256, and CI passes `github.base_ref` to scripts through `env` only. Why: downloads ran unchecked, and an expression in `run:` is interpolated into the shell (P3-2, P3-4).
- `check-config` runs the daemon's config, pinning and disk-bound checks without starting it, probing the quota on a spare box (selftest covers the languages file): an install runs it before switching, so a config these checks refuse fails before the switch, not in a restart loop.
- A conformance step waits 5 s of time the host ran the test, not 5 s of wall clock (extension capped at 60 s): a starved host must not fail a scenario, and a hung peer on a healthy host still fails in 5 s.
- The conformance replay reports each transcript `cases` message with one `Reporter::cases` call, which the daemon batches as one arrival: the batch age (100 ms) must not split a scripted message on a starved host. Grading reports case by case and never calls it.
- The standard checker's whitespace is C `isspace` (space, \t, \n, \v, \f, \r): the legacy checker split on it, so a rejudge of a migrated submission whose output uses a vertical tab must stay AC.
- An assignment with a time limit outside (0, 3600] s (zero, negative, NaN) or a memory limit outside [1, i32::MAX] KiB ends as an internal error before grading: a zero time limit leaves only the wall clock bounding a run, and it is never graded without a CPU limit.
- The sorted, easy, linecount and rstripped checkers use the same byte whitespace as standard (C `isspace`, with \v): the legacy versions split, stripped and removed whitespace on bytes with exactly that set, so \x1c-\x1f stay ordinary bytes.
- The linecount checker counts a whitespace-only line as a line (compared trimmed, so as empty), as the legacy checker did: only truly empty lines are dropped, so `a` and `a` plus a spaces-only line differ.
- A missing `<root>/<code>` directory is `DataError::Unavailable` (`RETRY DATA_UNAVAILABLE`), not an i/o error (COR-18): the data is not there yet (not synced, or a rename the bridge has not caught up with), so the run is retried with fresh inputs instead of ending as IE.
- `limits_error` refuses a time limit below 0.01 s and a memory limit below 1024 KiB, the backend and bridge minimums (V-2): isolate keeps the CPU limit in whole milliseconds, so a limit under 1 ms was 0, meaning no CPU limit, and under 1 MiB the `{memory_mib}` placeholder (a JVM `-Xmx`) is 0.
- The change-file check skips PRs from `release/*` branches: `knope release` consumes every change file, so a release PR has none to add, and the placeholder `release-<version>.md` note it needed leaked into the next changelog.
- The conformance manifest has a C program that wraps its answer in vertical tabs and expects AC, so every install proves on its host that the standard checker treats \v as whitespace (a one-token problem has no mirror that splits).
- Split signature (`signature_grader.split`) grades the author's `entry` and the contestant's functions in two isolate boxes joined by two pipes, with C++ glue generated from the problem header (sandbox bug hunt L1): the contestant's box holds only its own program. Roles come from the compiled entry (defined = callback, referenced = contestant function), so existing graders convert with no author edits; a header outside grammar v1 is a problem fault (IE), never a wrong verdict. `split: false` keeps the one-process path byte for byte until the backend switches a problem.
- Split signature time is counted in CPU, as one process counted it: the contestant is charged its own box's CPU plus the jury CPU spent in the callbacks it called (and the `const&` refresh before each frame), which the jury records in a file of its box; jury work outside callbacks is not charged. A contestant wall timeout is IE only when the jury's own CPU used the waiting time (`stalled_by_jury`, as for an interactor), and a jury over its own time limit is IE; no contestant exit code, signal or output gives IE or RETRY. A failed jury build is never cached: a missing tool or sandbox failure is RETRY, a grader that does not build is IE for that submission.
- Each value-returning split call costs the contestant one pipe round trip on its core, two context switches: measured 2.7-3.2 us on an idle host and up to ~7 us on a loaded one (the runtime adds nothing measurable over a bare pipe pair; memfd+futex is ~10 % cheaper). Below 1 us needs the jury on another core with a spinning wait (0.06 us measured on an SMT pair), i.e. the paired lane (`cores: 2`), not built. So a problem switches to split only after its model solution and every stored accepted solution pass under split, on the production judge, at no more than half the TL on every case (2x margin) in the rejudge audit; a `const&` result is compared in full before every frame (O(size) per frame), which the same gate covers.
- `extract_zip` refuses an archive the backend's reader (yauzl) would read differently (backend-v2#293): one whose central directory is not the one its last end record names, or that has a prefix offset (the crate falls back to an earlier end record, possibly an archive stored inside an entry, when the last one's directory does not parse); an entry with more than one Unicode Path field or one of another version than 1 (the crate takes the last of any version, yauzl the first valid version-1 one); a name with a control character (the backend shows CP437 control bytes as symbols, so no case can name it). It also refuses a central directory read with another record count than the end record names (a fallback end record can name the same start with fewer records), and an entry whose bytes differ from its declared size (the backend's reader refuses to read such an entry, so the judge graded bytes no one checked). Why: these archives were graded against files the backend never listed or checked. The backend refuses the same archives at upload; the contract fixtures check both sides.
- `cache_max_bytes` must be at least `MIN_CACHE_MAX_BYTES` (4 GiB, twice the backend's 2 GiB archive cap), checked by `check-config` and at daemon start; `check-config` also refuses a `problem_data_root` that is not a directory. Why: one archive may fill half the cache, so a smaller cache turns a valid upload into IE on every submission, and a missing data root makes every run wait for data that never comes.
- Backend contract fixtures (`crates/problem/tests/fixtures/judge-contract`, CONTRIBUTING.md): a copy of what the backend writes and accepts, checked by the judge's real parser, planner, checker setup and extractor. Why: three init.yml and archive mismatches reached production because each side tested only itself.
- A checker or interactor stream is read through a 64 KiB window at the end that holds what is read (themis stdout and testlib stderr, shown as details: the tail; `default` stdout: the head), whole lines only. Reading the whole stream would cost up to 64 MiB per stream per case.
- testlib checkers and interactors are built with `-DTESTSYS` (part of the helper cache key) and run with a judge-created result file (`.result.txt`, no `-appes`), and the exit code is the verdict: 0 AC, 1 WA, 2/4 PE, 8 EOF (WA), 3 IE, 7 the leading number of the result message as points, or, when the result file is empty (a program not built on testlib), a last stderr line that is exactly `points <number>` (not a number or outside the case: IE), 50+n `_pc(n)` = n/200 (only with testlib's own result-file line on stderr), anything else IE. Why: the result file holds only testlib's own message, and without `TESTSYS` `_pc(0..8)` exits like ok/wa/pe/fail/points/eof; `-appes` would turn `quitf(_points, ...)`, which live checkers and an interactor use, into a fail.
- A `default` checker whose share is followed on the same line by more than 64 KiB of output is a checker error (IE): only whole lines are read from a stream longer than the window.
- JAVA, JAVA8 and KOTLIN `preload` the JDK's `lib` (read into the page cache from the judge before each compile and run, `sandbox/src/preload.rs`). Why: the kernel charges page cache to the cgroup that first reads it, so a JVM first to read libjvm.so, the CDS archive and lib/modules after eviction reported 46 MiB more (80 MiB with the source launcher) than one that came after, which moved MLE and the shown memory with the host's page-cache state.
- PYPY3 `preload`s both layouts: a portable PyPy's `{runtime}/bin` and `{runtime}/lib` (`{runtime}`: the install above the run command's real file, never `/`, `/usr/local` or a directory one level below `/`; its entries are dropped where it does not resolve) and Ubuntu's `pypy3` package, which production runs (`/usr/lib/x86_64-linux-gnu/libpypy3.9-c.so`, `/usr/lib/pypy3.9`). Other preload entries are absolute paths taken as written, never `/`, `/usr` or `/usr/local` themselves; `check-config` and the daemon's start warn only when none of a language's preload paths exists. Why: a PyPy first to read libpypy and its start-up stdlib reported 58 MiB more (83 vs 24 MiB for a hello world) with no reserve above the limit. Known limit: a preloaded page reclaimed between the preload and the run's first touch of it is still charged to the box; preload runs right before every compile and run, so the window is short, and protecting the pages (`MemoryLow=`) would need host-wide slice config, out of scope.
- `output_limit_length: 0` is invalid (2026-10-25): the planner refuses a problem, batch or case limit of 0 (an unset one still takes `default_output_limit`); -1 already fails to parse as a `u64`. Why: 0 was read literally, so any output was OLE; the backend refuses it at save too (owner ruling).
- `output_limit_length: 0` is invalid (2026-10-25): the planner refuses a problem, batch or case limit of 0 (an unset one still takes `default_output_limit`); -1 already fails to parse as a `u64`. `check-config` and the daemon start also refuse `default_output_limit = 0`. Why: 0 was read literally, so any output was OLE; the backend refuses it at save too (owner ruling).
- PY3 and RUBY `preload` Ubuntu's interpreter, libpython/libruby and stdlib; a preload entry may end in a name and `*` (`/usr/lib/python3*`), expanded at load to the directory entries starting with that name. Why: measured with the runtime's files out of the page cache, a CPython hello world reported 10.4 MiB instead of 3.2 and a Ruby one 10.5 instead of 5.5, against problems limited to 2.5-16 MiB; a wildcard avoids writing the Python/Ruby version.
